# Заметки по решению

## Что сделано

### Задача 1. Распределение заказов

- Починен баг в `findNearest`: в вызове `distanceKm` у филиала были перепутаны местами широта и долгота (`b.lon, b.lat` вместо `b.lat, b.lon`), из-за чего ближайшим оказывался не тот филиал.
- Дописаны правила `pickup_point` и `city`, порядок правил: manual, single, pickup_point, city, geo, unassigned.
- Правило `geo`: если в городе заказа несколько филиалов, выбирается ближайший из них, иначе ближайший из всех. Если ближайший дальше 42 км, заказ возвращается с `{ branchId: null, rule: "too_far" }`.
- Дневной лимит (`dailyLimit`) считается по суткам Алматы (UTC+5) от `createdAt`. Если выбранный правилом single/pickup_point/city/geo филиал заполнен, заказ уходит в ближайший незаполненный (правило geo), если такого нет, то `unassigned`. Правило `manual` лимит не проверяет.
- API: `POST /orders/:id/assign` (идемпотентный, повторный вызов не занимает лимит снова), `GET /branches/:id/load?date=`.

### Задача 2. Онлайн-запись

- Починен баг в `overlaps`: интервалы, которые касаются краями (конец одного равен началу другого), больше не считаются пересечением (строгие `<` вместо `<=`).
- `getSlots`: шаг 15 минут, услуга целиком помещается в рабочее время, не пересекает перерывы и активные записи (отменённые не мешают), начинается позже текущего момента. После каждой записи у мастера технический перерыв 7 минут, в это время слоты не выдаются.
- API: `GET /masters/:id/slots`, `POST /bookings` (нормализация телефона к `+77XXXXXXXXX`, проверка слота, защита от двойного бронирования), `DELETE /bookings/:id` (отмена, запрет менее чем за 2 часа, повторная отмена без ошибки).

## Принятые допущения

- Лимит 42 км применяю только к основному правилу `geo`. При переполнении лимита fallback выбирает ближайший незаполненный филиал без ограничения 42 км: в README это описано как отдельная ветка.
- Технический перерыв 7 минут считаю как хвост после существующей записи (`[start, end + 7]`). Новый слот сам по себе хвостовую уборку внутри рабочего дня не резервирует: это одна строчка, если потребуется другое поведение.
- Телефон считаю валидным, если после очистки получается 11 цифр, начинающихся с `77` (казахстанский мобильный). Формы `+7...`, `8...` и локальные 10 цифр приводятся к этому виду.
- Коды ошибок, которые не заданы в README явно (например `not_found`, `invalid_phone`), выбраны по смыслу.

## Несколько инстансов и общая БД

### Задача 1 (лимит филиала)

Сейчас `assignments` и подсчёт загрузки живут в памяти одного процесса. При нескольких инстансах с общей БД состояние должно уехать в базу:

- Назначение заказа и инкремент счётчика филиала за сутки надо делать одной транзакцией. Иначе два инстанса одновременно прочитают «свободно» и оба назначат заказ сверх лимита.
- Загрузку филиала считать запросом к БД (`count` по branch_id и дате Алматы), а не держать в памяти.
- Идемпотентность `assign` обеспечить уникальным ключом по `order_id` (upsert или уникальный индекс): повторный запрос возвращает уже сохранённое назначение и не трогает счётчик.

### Задача 2 (одновременные записи)

Защита в памяти (`Set` занятых ключей) работает только внутри одного процесса. Для нескольких инстансов с PostgreSQL:

- Самое надёжное: уникальный индекс на `(master_id, start)` среди активных записей (partial unique index `where status = 'active'`). Вторая вставка в тот же слот падает по constraint, приложение отдаёт `409`. База гарантирует, что победит ровно один.
- Альтернатива: транзакция с `SELECT ... FOR UPDATE` по строке мастера или advisory-lock по ключу слота, чтобы сериализовать проверку слота и вставку.
- Проверку «слот свободен» и саму вставку обязательно делать в одной транзакции, иначе между чтением и записью успеет вклиниться другой инстанс.
